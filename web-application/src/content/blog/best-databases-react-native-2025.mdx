# Best Databases for React Native in 2025

Choosing a database for your React Native app isn't just about features on paper. It's about sync models that actually work offline, pricing that scales with your growth, and developer experience that doesn't waste your time.

I've seen teams rewrite their data layer multiple times because they picked based on hype instead of actual requirements. Let's talk about what actually matters when choosing between Supabase, Convex, InstantDB, Realm, and rolling your own backend.

---

## What Actually Matters

Before diving into specific databases, here's what separates a good choice from one that'll bite you later:

**Sync and offline support.** Most databases claim "offline-first," but there's a huge difference between caching queries and true local-first architecture. Can your app function completely offline? How does conflict resolution work when multiple users edit the same data?

**Developer experience.** This isn't fluffy—it's about iteration speed. How long does it take to add a new table? Change a schema? Debug why data isn't syncing? Bad DX compounds over time.

**Pricing structure.** Free tiers are great until you're not on them anymore. Look at what happens at 10K users, 100K users, 1M users. Some databases charge per row, others per API call, others per active connection. The math matters.

**When not to over-engineer.** Most apps don't need real-time collaboration on day one. Most don't need perfect offline support for every screen. Pick the simplest thing that handles your actual requirements, not your imagined ones.

---

## Supabase: SQL Power with Real-Time Extras

[Supabase](https://supabase.com) is PostgreSQL with a modern API layer. If you need structured data, complex queries, and room to grow, it's hard to beat.

### When Supabase Makes Sense

Your data is relational and you know it. Users have posts, posts have comments, comments have likes. Row-level security matters because users should only see their own data. You want real-time subscriptions but don't need full offline-first architecture.

Supabase generates REST and GraphQL APIs automatically from your schema. Auth is built-in with support for OAuth providers, magic links, and custom JWT claims. Edge functions let you run serverless code when you need custom logic.

The local development story is solid—Docker Compose gives you a full stack running locally, which means you can develop offline and test schema changes before pushing them.

### The Tradeoffs

Supabase's offline story is caching, not true local-first sync. You can use libraries like [@supabase/realtime-js](https://github.com/supabase/realtime-js) for subscriptions, but if your app needs to work completely offline with multi-user sync, you'll need to build that layer yourself.

Pricing scales with database size and usage. The free tier is generous (500MB database, 2GB bandwidth), but production apps will need at least the Pro plan ($25/month). Costs can climb if you have high bandwidth or need additional compute.

### DX Notes

Schema changes through the dashboard are straightforward. Migrations can be managed through the CLI or written as SQL. TypeScript types can be generated from your schema, which catches bugs before runtime.

The React Native integration is simple—just the JS client library. Real-time subscriptions work well for live updates, though you'll want to debounce UI updates to avoid jank.

**Best for:** Apps with structured data, complex queries, and standard auth requirements. Startups that want to move fast without managing infrastructure.

## Convex: Real-Time by Default

[Convex](https://convex.dev) is built around reactive queries. Your components subscribe to data and automatically update when anything changes—no manual refetching, no stale data.

### When Convex Makes Sense

You're building something collaborative or real-time. A chat app, a shared task list, a multiplayer game. Convex handles all the subscription plumbing automatically.

The developer experience is different from traditional databases. Instead of writing SQL, you write TypeScript functions that Convex runs server-side. These functions are transactional—reads and writes are automatically consistent.

```typescript
// This runs on the server, called from your React Native app
export const sendMessage = mutation(async ({ db }, { channel, text }) => {
  await db.insert("messages", { channel, text, timestamp: Date.now() });
});
```

Your React Native components subscribe to queries and get automatic updates:

```typescript
const messages = useQuery(api.messages.list, { channel: currentChannel });
// Automatically updates when new messages arrive
```

### The Tradeoffs

You're locked into Convex's execution model. All data access goes through Convex functions—you can't just write a raw SQL query or connect a third-party analytics tool directly to your database.

The pricing model is based on function execution time and bandwidth. The free tier (1M function calls/month, 1GB bandwidth) works for prototypes, but real apps will need paid plans.

Offline support exists but is less mature than Realm or InstantDB. Convex caches query results locally, but complex offline scenarios need careful handling.

### DX Notes

Schema is code. You define it in TypeScript, deploy it, and Convex handles migrations. This is great for version control but means schema changes require code deploys.

The built-in scheduler and cron jobs are handy for background tasks. File storage is integrated, so you're not juggling separate S3 buckets.

**Best for:** Real-time collaborative apps, teams that want everything handled (auth, storage, scheduling), projects where TypeScript-first is a feature, not a constraint.

## InstantDB: Local-First, Less Complexity

[InstantDB](https://instantdb.com) is the new kid focused on one thing: making local-first actually simple.

### When InstantDB Makes Sense

You want offline-first without the ceremony. InstantDB stores data locally in AsyncStorage (React Native) or IndexedDB (web) and syncs automatically. Queries run against local data, so they're instant.

The setup is minimal:

```typescript
import { init } from '@instantdb/react-native';

const db = init({ appId: 'your-app-id' });

function ChatScreen() {
  const { data, error } = db.useQuery({ messages: {} });
  // Data comes from local storage, syncs in background
}
```

Optimistic updates work by default. Write to local storage, show the change immediately, sync in the background. Conflicts are handled with last-write-wins (you can customize this).

### The Tradeoffs

InstantDB is young. The ecosystem is small, documentation is growing, and edge cases aren't all documented yet. If you hit a wall, you're more likely to be filing issues than finding solutions on Stack Overflow.

The relational query model is simpler than SQL but less powerful. Complex joins or aggregations might not be expressible. For many apps, this is fine—most mobile UIs show pretty simple data. For analytics or reporting, you'll need a separate solution.

Pricing isn't fully clear yet for production scale. The free tier exists, but long-term pricing for large apps is still evolving.

### DX Notes

The React hooks are clean. No separate state management library needed—InstantDB handles the reactivity.

The local-first model means your app works offline without extra code. This is huge for UX, especially on mobile where connectivity is unreliable.

**Best for:** Apps that need true offline-first without complex setup, teams that value simplicity over maximum flexibility, projects where the local-first model aligns with the product (collaborative tools, mobile-first apps).

## Realm: The Mobile-First Veteran

[Realm](https://realm.io) (now MongoDB Realm / Atlas Device SDK) has been the go-to mobile database for years. It's fast, fully offline, and battle-tested.

### When Realm Makes Sense

You need maximum performance for large datasets on-device. Realm is typically 2-10x faster than SQLite for mobile use cases. It runs directly on the device with zero latency for reads.

Realm's object model is intuitive—define schemas as classes, query with a fluent API:

```typescript
class Task extends Realm.Object {
  _id!: Realm.BSON.ObjectId;
  name!: string;
  completed!: boolean;
}

const tasks = realm.objects(Task).filtered('completed == false');
```

The [@realm/react](https://www.npmjs.com/package/@realm/react) library provides hooks that automatically re-render when data changes.

If you need server sync, Realm integrates with MongoDB Atlas. Device Sync handles conflict resolution, permissions, and real-time updates across devices.

### The Tradeoffs

Realm's setup is more involved than Supabase or InstantDB. You need to define schemas in code, manage migrations explicitly, and understand Realm's transaction model.

The query language isn't SQL. It's powerful for object traversal but less flexible for ad-hoc analytics. If you're used to SQL, there's a learning curve.

Device Sync with Atlas requires a MongoDB Atlas account and has its own pricing (based on sync hours and data transfer). For local-only use, Realm is free, but most production apps need sync.

### DX Notes

Performance is legitimately impressive. Queries on thousands of objects are instant. This matters for apps with large local datasets (offline maps, media libraries, etc.).

The migration story requires attention. Schema changes need migration functions. Realm won't auto-migrate—you handle it manually. This is good for production safety but adds friction during development.

**Best for:** Apps with large local datasets, offline-first requirements, and performance-critical queries. Mobile apps that treat the device as the source of truth, syncing to servers as a secondary concern.

## Custom Backend: When and Why

Sometimes none of these fit. You already have a Django or Rails backend, or you need custom business logic that doesn't map to these services.

### When a Custom Backend Makes Sense

You have complex server-side logic. Multi-step workflows, integrations with third-party APIs, payment processing with custom rules. Running that in edge functions or Convex functions feels wrong—you want a real server.

You're integrating with existing systems. Your company has a legacy database, microservices architecture, or internal APIs. Adding Supabase on top is extra complexity, not simplification.

You need specific compliance or data residency requirements. Some industries require full control over where data lives and how it's accessed.

### The Tradeoffs

You own everything. That means building auth, handling sync, managing deployments, monitoring uptime, dealing with scaling. For some teams, this is fine—it's their core competency. For others, it's distraction from product work.

Offline sync is on you. Building reliable local-first sync is hard. Libraries like [WatermelonDB](https://watermelondb.dev/) or [RxDB](https://rxdb.info/) can help, but you're still responsible for conflict resolution and edge cases.

### DX Notes

Iteration speed depends on your stack. A well-built backend with good tooling can be fast. A poorly maintained one becomes a bottleneck.

**Best for:** Teams with backend expertise who need full control, apps integrating with existing enterprise systems, scenarios where compliance or data requirements rule out third-party services.

## Decision Framework

Here's how to choose:

**Start with Supabase if:** You need structured data, SQL queries, and don't want to manage infrastructure. It's the safe default for most apps.

**Choose Convex if:** Real-time collaboration is central to your product and you want everything (auth, functions, storage) in one place.

**Pick InstantDB if:** Offline-first is non-negotiable and you value simplicity over ecosystem maturity.

**Use Realm if:** You're building a mobile-first app with large local datasets and need maximum performance.

**Build custom if:** You have specific requirements none of these solve, or you're integrating with existing systems.

**Don't over-engineer.** Most apps can start with Supabase or Firebase and be fine. You can always migrate later if you truly outgrow it. The risk isn't picking the wrong database—it's spending months building perfect infrastructure instead of validating your product.

---

## What Breaks at Scale

No matter which you choose, watch out for these:

**N+1 queries in lists.** Loading a feed of 50 items where each item triggers its own query. Batch your reads.

**Unfiltered subscriptions.** Subscribing to all messages in all channels when you only need the current one. Filter server-side.

**Storing binary data in your database.** Images, videos, large files—use object storage (S3, Cloudflare R2) and store URLs in your database.

**Not indexing queries.** If you're filtering on a field frequently, index it. This matters more as data grows.

---

## Conclusion

The best database is the one that matches your actual requirements, not the one with the most GitHub stars.

Supabase and Convex are both excellent defaults—Supabase for SQL power and flexibility, Convex for real-time without the plumbing. InstantDB is promising for true local-first apps. Realm is unbeatable for performance on large mobile datasets. Custom backends still make sense when you need full control.

Pick based on what your app actually needs today, not what you think you might need in three years. You can always change later, but the best way to learn what you really need is to ship something and watch how people use it.
